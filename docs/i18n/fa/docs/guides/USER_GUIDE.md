### حالت سینی سیستم

OmniRoute را در سینی سیستم اجرا کنید:

```bash
omniroute serve --tray
```

پس از آمادهشدن سرور و سینی سیستم، فرمان خاتمه مییابد.

سرور بدون ترمینال به کار خود ادامه میدهد.

حالت سینی سیستم از macOS، Windows و نشستهای گرافیکی Linux پشتیبانی میکند. حالت سینی سیستم داشبورد را بهطور خودکار باز نمیکند.

برای انجام اقدامات زیر از منوی سینی سیستم استفاده کنید:

- بازکردن داشبورد.
- بازکردن `/dashboard/logs`.
- تغییر راهاندازی خودکار.
- توقف OmniRoute.

از `--tray` همراه با گزینههای زیر استفاده نکنید:

- `--daemon`
- `--log`
- `--no-recovery`

این حالتها به مالکیت فرایند متفاوتی نیاز دارند.

راهاندازی در ورود بعدی به سیستم را فعال کنید:

```bash
omniroute autostart enable
```

راهاندازی خودکار در macOS، Windows و نشستهای گرافیکی Linux از حالت سینی سیستم استفاده میکند. Linux بدون رابط گرافیکی از سرویس کاربری systemd موجود استفاده میکند.

راهاندازی در هنگام ورود را غیرفعال کنید:

```bash
omniroute autostart disable
```

pkgname=omniroute
version=3.8.0
revision=1
hostmakedepends="nodejs python3 make"

maintainer="zenobit <zenobit@disroot.org>"
license="MIT"

export npm_config_loglevel=error
export npm_config_fund=false

do_build() {
	# تعیین معماری CPU هدف برای node-gyp
	local _gyp_arch
	case "$XBPS_TARGET_MACHINE" in
		aarch64*) _gyp_arch=arm64 ;;
		armv7*|armv6*) _gyp_arch=arm ;;
		i686*) _gyp_arch=ia32 ;;
		*) _gyp_arch=x64 ;;
	esac

	# 1) نصب تمام وابستگیها – بدون اجرای اسکریپتها
	NODE_ENV=development npm ci --ignore-scripts

	# 2) ساخت بسته مستقل Next.js
	npm run build

	# 3) کپیکردن داراییهای ایستا در بسته مستقل
	cp -r .next/static .next/standalone/.next/static
	[ -d public ] && cp -r public .next/standalone/public || true

	# 4) کامپایل بایندینگ بومی better-sqlite3
	local _node_gyp=/usr/lib/node_modules/npm/node_modules/node-gyp/bin/node-gyp.js

	local _bs3_release=.next/standalone/node_modules/better-sqlite3/build/Release
	mkdir -p "$_bs3_release"
	cp node_modules/better-sqlite3/build/Release/better_sqlite3.node "$_bs3_release/"

	# 6) حذف بستههای sharp مختص معماری
	rm -rf .next/standalone/node_modules/@img

	# 7) کپیکردن وابستگیهای زمان اجرای pino که توسط تحلیل ایستای Next.js حذف شدهاند:
	for _mod in pino-abstract-transport split2 process-warning; do
		cp -r "node_modules/$_mod" .next/standalone/node_modules/
	done
}

do_check() {
	npm run test:unit
}

do_install() {
	vmkdir usr/lib/omniroute/.next
	vcopy .next/standalone/. usr/lib/omniroute/.next/standalone

	# جلوگیری از حذف دایرکتوریهای خالی مسیریاب برنامه Next.js توسط هوک پس از نصب
	for _d in \
		.next/standalone/.next/server/app/dashboard \
		.next/standalone/.next/server/app/dashboard/settings \

#!/bin/sh
export PORT="${PORT:-20128}"
export DATA_DIR="${DATA_DIR:-${XDG_DATA_HOME:-${HOME}/.local/share}/omniroute}"
export APP_LOG_TO_FILE="${APP_LOG_TO_FILE:-false}"

exec node /usr/lib/omniroute/.next/standalone/server.js "$@"
EOF

### ارائه دهندگان سفارشی سازگار با OpenAI

هر دروازه ای که از OpenAI API صحبت می کند (پراکسی خود میزبان، vLLM، جمع کننده شخص ثالث) می تواند به عنوان گره ارائه دهنده خود اضافه شود:

1. **ارائه دهندگان → افزودن OpenAI سازگار** .
2. **نام** : یک برچسب نمایشگر برای گره.
3. **پیشوند** : نام مسیریابی مشتریان مدل ها را به عنوان `<prefix>/<model>` می نامند، بنابراین یک گره با پیشوند `mygw` `mygw/gpt-4o-mini` را ارائه می دهد. مورد نیاز؛ هیچ محدودیتی برای شخصیت وجود ندارد
4. **نوع API** : خانواده نقطه پایانی که درگاه ارائه میکند (تکمیلهای چت، پاسخها، جاسازیها، صدا، تصاویر).
5. **پایه URL** : ریشه API ، تا و شامل `/v1` (مثلا `https://gateway.example.com/v1`)، نه مسیر کامل `/chat/completions`. دروازه هایی با مسیرهای غیر استاندارد آنها را در زیر قرار می دهند** تنظیمات پیشرفته** (مسیر چت، مسیر مدل ها).
6. این** کلید API (برای چک)** فیلد فقط اتصال را آزمایش می کند. پس از ایجاد گره، آن را باز کرده و استفاده کنید** افزودن اتصال** برای ذخیره کلیدی که درخواست ها از آن استفاده خواهند کرد.

گره یک شناسه داخلی به شکل `openai-compatible-<apiType>-<uuid>` دریافت می کند. شما هرگز نیازی به تایپ آن ندارید، پیشوند نام عمومی است.

#### پیشوندهای رزرو شده

یک پیشوند نمی تواند شناسه یا نام مستعار یک ارائه دهنده داخلی (به عنوان مثال `openai`، `cf`) و یا شناسه یک ارائه دهنده بازنشسته باشد. حلکننده مدل، شناسهها و نامهای مستعار داخلی را قبل از گرههای سفارشی بررسی میکند، بنابراین گرهای که یکی از آن پیشوندها را استفاده میکند، هرگز ترافیک دریافت نمیکند: `<prefix>/model` به جای آن به ارائهدهنده داخلی میرود، یا اگر آن ارائهدهنده بازنشسته شود، بسته نمیشود. ایجاد یا ویرایش یک گره با چنین پیشوندی رد می شود:

```text
prefix: "<prefix>" is a reserved provider prefix — choose a different prefix (reserved ids/aliases cannot be used for custom nodes because requests like <prefix>/model route to a built-in provider or fail closed when retired)
```

یک پیشوند متمایز (`mygw`، `acme-proxy`) انتخاب کنید. اگر درخواستها به یک گره سفارشی با خطای نامگذاری یک ارائهدهنده داخلی یا اعتبار آن با شکست مواجه شد، بررسی کنید که آیا پیشوند گره رزرو شده است: گرههایی که قبل از وجود این قانون ذخیره شدهاند هنوز ذخیره میشوند، اما پیشوند آنها به ارائهدهنده داخلی میرود. گره را ویرایش کنید و یک پیشوند جدید به آن بدهید.

#### گزینه های دروازه هر اتصال

این کلیدها در `providerSpecificData` یک اتصال قرار می گیرند (به عنوان مثال از طریق `PUT /api/providers/{id}`):

- `toolNameMaxLength` (عدد صحیح، 1-1024) - برای اتصالات سازگار با قالب چت OpenAI که دروازه آنها نام ابزار طولانی را رد می کند. نام های طولانی تر به عنوان نام مستعار کوتاه ارسال می شوند و در پاسخ بازیابی می شوند.
- `quotaEndpoint` - نقطه پایانی quota/credits دروازه، نوار سهمیه داشبورد و مسیریابی آگاه از سهمیه را بخوانید. بر روی هر دو اتصال OpenAI و Anthropic سازگار کار می کند. شکل کامل در `open-sse/services/usage/openaiCompatible.ts` مستند شده است.

### زنجیر زدن همتایان OmniRoute

دروازه OmniRoute دیگری را می توان به عنوان یک اضافه کرد** سازگار با OpenAI سفارشی** ارائه دهنده از پایه `/v1` URL همتا و یک کلید اختصاصی API با حداقل امتیاز صادر شده توسط آن همتا استفاده کنید.

برای زنجیره های متقابل یا چند جهشی، محافظ حلقه انتخابی را در هر دروازه فعال کنید:

```bash
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

```bash
# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

فقط درخواستهایی که به یک همتا URL به طور صریح در فهرست مجاز ارسال میشوند، سرصفحه `X-OmniRoute-Peer-Trace` را دریافت میکنند. یک دروازه، یک مثال مکرر ID یا بودجه پایان یافته را با HTTP `508 Loop Detected` رد می کند. ارائه دهندگان عادی بالادستی هیچ ابرداده ای دریافت نمی کنند.

زنجیره همتا، تکرار پایگاه داده یا شکست میزبان نیست. هر دروازه ای حالت SQLite ، حافظه پنهان، شمارنده نرخ و جلسات مستقل را نگه می دارد. برای در دسترس بودن active/passive یا active/active از یک پروکسی معکوس یا کلاینت بررسیشده سالم استفاده کنید و هرگز یک پایگاه داده SQLite را در چندین نمونه در حال OmniRoute نصب نکنید.

- برای تغییر روش انتقال مدیریت‌شده، مقدار `CLOUDFLARED_PROTOCOL` را روی `quic` یا `auto` قرار دهید.
- اگر ترجیح می‌دهید به‌جای دانلود مدیریت‌شده از فایل اجرایی ازپیش‌نصب‌شده `cloudflared` استفاده کنید، `CLOUDFLARED_BIN` را تنظیم کنید.

- ابتدا فقط در صورت نیاز `cloudflared` را فعال می کند. بعداً از همان باینری مدیریت شده مجدداً استفاده می کند
- تونل های سریع پس از راه اندازی مجدد OmniRoute یا کانتینر به طور خودکار بازیابی نمی شوند. در صورت نیاز آنها را از داشبورد دوباره فعال کنید

- تونل های سریع مدیریت شده به طور پیش فرض برای حمل و نقل HTTP/2 برای جلوگیری از هشدارهای بافر پر سر و صدا QUIC UDP در کانتینرهای محدود

- اگر ترجیح می دهید به جای دانلود مدیریت شده از یک باینری `cloudflared` از پیش نصب شده استفاده کنید `CLOUDFLARED_BIN` تنظیم کنید
- پنلهای تونل سریع Cloudflare ، قیف Tailscale و ngrok تونل را میتوان در آن نشان داد یا پنهان کرد.** تنظیمات → ظاهر** . مخفی کردن یک پانل باعث توقف یک تونل در حال اجرا نمی شود.

### LLM Gateway Intelligence (فاز 9)

- **ردیابی پیشرفت** - رویدادهای SSE `event: progress` را از طریق هدر `X-OmniRoute-Progress: true` انتخاب کنید

   - **دوره انتظار پایه** — بازه پیش‌فرض انتظار برای خطاهای قابل‌تلاش مجدد سرویس بالادستی
   - **استفاده از راهنمای تلاش مجدد سرویس بالادستی** — رعایت مقدار معتبر `Retry-After` یا راهنمای بازنشانی در صورت ارائه
   - **حداکثر مراحل عقب‌نشینی** — بیشترین سطح عقب‌نشینی نمایی برای خطاهای تکراری

3. **مدارشکن ارائه‌دهنده** — خطاهای سرتاسری ارائه‌دهنده را پایش می‌کند و پس از رسیدن به آستانه تعیین‌شده، مدار را خودکار باز می‌کند:
   - **آستانه خطا** — تعداد خطاهای پیاپی ارائه‌دهنده پیش از بازشدن مدار
   - **مهلت بازنشانی** — بازه زمانی پیش از آزمایش دوباره ارائه‌دهنده
   - **CLOSED** (سالم) — درخواست‌ها به‌طور عادی جریان دارند
   - **OPEN** — ارائه‌دهنده پس از خطاهای تکراری موقتاً مسدود می‌شود
   - **HALF_OPEN** — بازیابی ارائه‌دهنده در حال آزمایش است

   محدودیت نرخ `429` در سطح اتصال داخل **Connection Cooldown** باقی می‌ماند و در مدارشکن ارائه‌دهنده محاسبه نمی‌شود.

   وضعیت زمان اجرای مدارشکن ارائه‌دهنده فقط در **Dashboard → Health** نمایش داده می‌شود.

4. **انتظار برای پایان دوره توقف** — اگر همه اتصال‌های نامزد در دوره انتظار باشند، OmniRoute می‌تواند تا پایان نخستین دوره منتظر بماند و همان درخواست کارخواه را خودکار دوباره اجرا کند.

5. **تشخیص خودکار محدودیت نرخ** — وقتی ارائه‌دهنده بالادستی بازه انتظار صریحی برمی‌گرداند، در صورت فعال‌بودن این تنظیم، آن راهنما جایگزین دوره انتظار محلی اتصال می‌شود.

**نکته کاربردی:** پس از اختلال، برای بررسی و بازنشانی مدارشکن‌های فعال ارائه‌دهندگان از صفحه **Health** استفاده کنید. صفحه Resilience فقط پیکربندی را تغییر می‌دهد.

### ارتجاعی و مدار شکن

پیکربندی از طریق** تنظیمات داشبورد → → Resilience** .

OmniRoute انعطاف پذیری در سطح ارائه دهنده را با پنج جزء پیاده سازی می کند:

1. **درخواست صف و سرعت** - شکل دهی درخواست در سطح سیستم:
   - **درخواست در دقیقه (RPM)** - حداکثر درخواست در دقیقه برای هر حساب
   - **حداقل زمان بین درخواست ها** - حداقل فاصله بین درخواست ها در میلی ثانیه
   - **حداکثر درخواست همزمان** - حداکثر درخواست همزمان برای هر حساب

2. **خنک شدن اتصال** - پیکربندی از نوع Per-auth برای یک اتصال واحد پس از خرابی های قابل امتحان مجدد:
   - **خنک کننده پایه** - پنجره خنک کننده پیش فرض برای خرابی های بالادستی قابل امتحان مجدد
   - **از نکات «آزمایش مجدد بالادست» استفاده کنید** - در صورت ارائه به نکات معتبر `Retry-After` یا تنظیم مجدد احترام می گذارد
   - **حداکثر مراحل عقب نشینی** - حداکثر سطح عقب نشینی نمایی برای شکست های مکرر

3. **مدار شکن ارائه دهنده** - خرابیهای ارائهدهنده سرتاسر را ردیابی میکند، ارائهدهندهای را که در آستانه هشدار پیکربندیشده تنزل یافته، علامتگذاری میکند، و با رسیدن به آستانه شکست پیکربندیشده، شکن را باز میکند:
   - **آستانه تخریب** - خرابی های متوالی ارائه دهنده قبل از ورود به `DEGRADED`
   - **آستانه شکست** - خرابی های متوالی ارائه دهنده قبل از ورود به `OPEN`
   - **بازنشانی مهلت زمانی** - پنجره زمانی قبل از آزمایش مجدد ارائه دهنده
   - **CLOSED** (سالم) - درخواست ها به طور معمول جریان دارند
   - **DEGRADED** - در حالی که خرابیهای بالا ردیابی میشوند، درخواستها همچنان جریان دارند
   - **OPEN** - ارائه دهنده به طور موقت پس از خرابی های مکرر مسدود می شود
   - **HALF_OPEN** - آزمایش اینکه آیا ارائه دهنده بهبود یافته است

   محدودیتهای نرخ `429` در محدوده اتصال باقی میمانند** خنک شدن اتصال** و در میان شکن ارائه دهنده حساب نمی شود.

   وضعیت زمان اجرا قطع کننده ارائه دهنده روشن نشان داده شده است** داشبورد → Health** فقط

4. **منتظر خنک شدن باشید** - اگر هر اتصال کاندید از قبل خنک می شود، OmniRoute می تواند منتظر اولین خنک شدن بماند و به طور خودکار همان درخواست مشتری را دوباره امتحان کند.

5. **تشخیص خودکار محدودیت نرخ** - هنگامی که ارائه دهندگان بالادست پنجرههای انتظار صریح را برمیگردانند، این نکات زمانی که تنظیم فعال میشود، خنککردن اتصال محلی را لغو میکند.

**نکته حرفه ای:** استفاده کنید** سلامتی** صفحه ای برای بازرسی و بازنشانی بریکرهای ارائه دهنده زنده پس از قطع شدن. صفحه Resilience فقط پیکربندی را تغییر می دهد.

| **Round-Robin**        | مدل‌ها را به‌ترتیب و به‌صورت چرخشی انتخاب می‌کند.                                      |
| **Priority**           | همیشه ابتدا مدل اول را امتحان می‌کند و فقط در صورت خطا سراغ مدل جایگزین می‌رود.       |
| **Random**             | برای هر درخواست، یک مدل را به‌صورت تصادفی از ترکیب انتخاب می‌کند.                      |
| **Weighted**           | درخواست‌ها را متناسب با وزن تعیین‌شده برای هر مدل هدایت می‌کند.                       |
| **Least-Used**         | درخواست را به مدلی با کمترین تعداد درخواست اخیر می‌فرستد و از معیارهای ترکیب بهره می‌گیرد. |
| **Cost-Optimized**     | با استفاده از جدول قیمت، درخواست را به ارزان‌ترین مدل موجود هدایت می‌کند.             |

پیش‌فرض‌های سراسری ترکیب را می‌توان در مسیر **Dashboard → Settings → Routing → Combo Defaults** تنظیم کرد.

### استراتژی های متعادل کننده ترکیبی

تعادل در هر ترکیب را پیکربندی کنید** داشبورد → Combos → Create/Edit → استراتژی** .

| استراتژی             | توضیحات                                                                        |
| -------------------- | ------------------------------------------------------------------------------ |
| **دور رابین**        | به صورت متوالی در میان مدل ها می چرخد                                          |
| **اولویت**           | همیشه مدل اول را امتحان می کند. فقط به خطا برمی گردد                           |
| **تصادفی**           | برای هر درخواست یک مدل تصادفی از ترکیب ترکیبی انتخاب می کند                    |
| **وزن دار**          | مسیرها به طور متناسب بر اساس وزن های اختصاص داده شده در هر مدل                 |
| **کمترین استفاده**   | مسیرهایی به مدل با کمترین درخواست های اخیر (از معیارهای ترکیبی استفاده می کند) |
| **بهینه سازی هزینه** | مسیرها به ارزان ترین مدل موجود (از جدول قیمت استفاده می کند)                   |

پیش فرض های جهانی ترکیبی را می توان در آن تنظیم کرد** تنظیمات داشبورد → → مسیریابی → پیشفرض ترکیبی** . مهلت زمانی هدف ترکیبی به طور پیشفرض مهلت زمانی درخواست فعلی را به ارث میبرد. استفاده کنید** مهلت زمانی هدف (ثانیه)** در پیشفرضهای ترکیبی یا ترکیبی تکی تنها زمانی که یک محدودیت کوتاهتر برای هر هدف باید بازگشت سریعتری ایجاد کند.

بهینهسازیهای ترکیبی با تأخیر صفر انتخابی هستند. ترک کنید** بهینه سازی با تاخیر صفر** برای جلوگیری از مسابقه دادن به اهداف بازگشتی، پرش از اهداف بر اساس تاریخچه TTFT یا فشرده سازی درخواست های بازگشتی، این ویژگی های تأخیر غیرفعال است. فعال کردن آن اجازه می دهد تا پوشش پیکربندی شده، پرش های پیش بینی کننده TTFT ، و فشرده سازی بازگشتی فعال برای معامله وفاداری routing/request با تأخیر دم کمتر.

غیر فعال کردن** بافر توکن استدلال** هنگامی که ارائه دهندگان بالادستی به محدودیت های سختگیرانه `max_tokens` / `maxOutputTokens` نیاز دارند. هنگامی که فعال باشد، مسیریابی ترکیبی تنها فضای سر مدل استدلالی را برای مدلهایی با درپوش خروجی مشخص اضافه میکند و زمانی که مقدار بافر ایمن از آن سقف فراتر رود، محدودیت توکن کلاینت را بدون تغییر میگذارد. اگر محدودیت کلاینت از قبل بالاتر از یک سقف شناخته شده باشد، OmniRoute قبل از ارسال درخواست بالادستی، آن را به آن سقف میبندد.

## 🤖 مسیریابی خودکار (بدون نیاز به پیکربندی)

OmniRoute همراه با یک **مسیریاب خودکار مبتنی بر امتیازدهی** عرضه میشود که برای هر درخواست، بهترین مدل را از میان تمام ارائهدهندگان متصل انتخاب میکند — بدون نیاز به نگهداری هیچ ترکیبی. کافی است درخواست را با یکی از پیشوندهای `auto/*` ارسال کنید؛ OmniRoute در لحظه یک ترکیب مجازی میسازد و گزینهها را بر اساس تأخیر، هزینه، نرخ موفقیت، تناسب پنجره زمینه، مناسببودن مدل برای وظیفه، خطاهای اخیر، سهمیه و وضعیت قطعکننده مدار امتیازدهی میکند.

| پیشوند         | معیار بهینهسازی                                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| `auto`         | حالت پیشفرض متعادل (تأخیر × هزینه × نرخ موفقیت)                                                                   |
| `auto/coding`  | وظایف برنامهنویسی: Claude، GPT-5، GLM، Kimi، Qwen Coder و مدلهای برنامهنویسی DeepSeek را ترجیح میدهد              |
| `auto/cheap`   | کمترین هزینه بهازای هر توکن؛ تأخیر بیشتر را میپذیرد                                                               |
| `auto/fast`    | کمترین تأخیر؛ هزینه را نادیده میگیرد                                                                              |
| `auto/offline` | فقط ارائهدهندگان محلی (Ollama، vLLM، llama.cpp) — مناسب برای محیطهای ایزوله از شبکه                               |
| `auto/smart`   | اولویت با کیفیت استدلال (Opus، GPT-5 xhigh، R1، استدلال GLM 5.1)                                                  |
| `auto/lkgp`    | «آخرین ارائهدهنده مطلوب شناختهشده» — ابتدا به آخرین ارائهدهنده موفق متصل میماند، سپس به قوانین جایگزین رجوع میکند |

مثال:
>>>>>>> upstream/main

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer $OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto/coding",
    "messages": [{ "role": "user", "content": "این تابع Python را بازآرایی کن" }],
    "stream": true
  }'
```

مسیریاب خودکار بهطور کامل در [AUTO-COMBO.md](../routing/AUTO-COMBO.md) توضیح داده شده است — از جمله نحوه تنظیم وزنهای امتیازدهی، قراردادن ارائهدهندگان در فهرست سیاه و بررسی تصمیمهای مسیریابی در **داشبورد ← ترکیب خودکار**.

## 🔌 یکپارچهسازی MCP و A2A

OmniRoute هم یک **سرور MCP** (پروتکل زمینه مدل) و هم یک **سرور A2A** (JSON-RPC 2.0 عاملبهعامل) است. هر محیط توسعه یا میزبان عامل سازگار با MCP میتواند ابزارهای OmniRoute را مستقیماً فراخوانی کند — بدون نیاز به هیچ پوشش اضافی.

### روشهای انتقال MCP

- **SSE**: `http://localhost:20128/api/mcp/sse`
- **HTTP قابلجریان**: `http://localhost:20128/api/mcp/stream`
- **stdio**: `omniroute --mcp` (برای افزونههای محیط توسعه که stdio را ترجیح میدهند)

### اتصال Claude Desktop

فایل `~/Library/Application Support/Claude/claude_desktop_config.json` را در macOS، یا فایل معادل آن را در Windows/Linux ویرایش کنید:

```json
{
  "mcpServers": {
    "omniroute": {
      "command": "omniroute",
      "args": ["--mcp"]
    }
  }
}
```

### اتصال Cursor / Continue / VS Code MCP

از URL مربوط به SSE یعنی `http://localhost:20128/api/mcp/sse` و یک کلید API از نوع Bearer که در **داشبورد ← کلیدهای API** ایجاد شده است، استفاده کنید.

### دامنهها

MCP در حال حاضر 32 دامنه نامگذاریشده تعریف میکند. هر کلید Bearer را میتوان به دامنههای مشخصی محدود کرد — برای فهرست مرجع دامنهها و ابزارها به [MCP-SERVER.md](../frameworks/MCP-SERVER.md) و برای طرحواره JSON-RPC به [A2A-SERVER.md](../frameworks/A2A-SERVER.md) مراجعه کنید.

## 🧠 سیستم مهارتها

OmniRoute یک **چارچوب مهارت** توسعهپذیر (`src/lib/skills/`) ارائه میدهد تا عاملها و نقطه پایانی A2A بتوانند روالهای مختص دامنه را اجرا کنند (برای مثال `code-review`، `summarize`، `extract-facts` و `web-research`).

- **دامنههای اختصاصی هر کلید** — مشخص کنید کدام کلیدهای API میتوانند کدام مهارتها را فراخوانی کنند
- **مهارتهای سفارشی** — یک فایل TypeScript را در `src/lib/a2a/skills/` قرار دهید و آن را ثبت کنید تا بلافاصله از طریق A2A قابل فراخوانی شود

## 💾 سیستم حافظه

OmniRoute **حافظه مکالمهای بلندمدت** را با بازیابی ترکیبی ذخیره میکند:

- **SQLite FTS5** برای جستوجوی کلیدواژهای در نوبتهای مکالمه گذشته
- **ذخیرهساز برداری Qdrant** (اختیاری) برای یادآوری معنایی
- **استخراج خودکار واقعیتها** — موجودیتها، ترجیحات و تصمیمها پس از هر نشست خلاصه شده و در جدول `memory_facts` ذخیره میشوند
- حافظهها بهازای هر کلید API و هر نشست تفکیک میشوند

حافظهها را در **داشبورد ← حافظه** مدیریت کنید (جستوجو، ویرایش، برونبری و پاکسازی). رابط HTTP (`/api/memory/*`) به عاملها اجازه میدهد واقعیتها را بهصورت برنامهنویسیشده ارسال و جستوجو کنند — به [MEMORY.md](../frameworks/MEMORY.md) مراجعه کنید.

## 🔔 وبهوکها

برای پایش و خودکارسازی بلادرنگ، در رویدادهای OmniRoute مشترک شوید.

- در مسیر **داشبورد ← وبهوکها** یک وبهوک با URL مقصد و کلید محرمانه امضای HMAC ایجاد کنید
- رویدادهای موجود: `request.completed`، `request.failed`، `provider.unavailable`، `budget.exceeded`، `combo.switched`، `circuit_breaker.opened`، `circuit_breaker.closed`
- هر بار ارسالی برای اعتبارسنجی شامل `X-OmniRoute-Signature` (HMAC-SHA256) است
- تلاشهای مجدد: 3 تلاش با تأخیر تصاعدی، سپس انتقال به صف نامههای مرده

## 🛠️ مدیریت برنامهنویسیشده

میتوانید تمام منابع OmniRoute (ارائهدهندگان، ترکیبها، کلیدها و تنظیمات) را از طریق HTTP و با استفاده از یک **کلید Bearer دارای دامنه `manage`** مدیریت کنید.

کلید را در مسیر **داشبورد ← کلیدهای API ← کلید جدید ← دامنه: manage** ایجاد کنید، سپس:

```bash
# فهرست ارائهدهندگان
curl http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"

# افزودن اتصال ارائهدهنده
curl -X POST http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "provider": "openai", "apiKey": "sk-...", "name": "main" }'

# ایجاد یک ترکیب
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "premium", "strategy": "priority", "models": [{ "model": "cc/claude-opus-4-7" }, { "model": "glm/glm-5.1" }] }'

# فهرستکردن/ایجاد کلیدهای API
curl http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"
curl -X POST http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -d '{ "name": "ci-bot", "scopes": ["chat"] }'
```

برای مشاهده فهرست کامل نقاط پایانی و طرحوارههای درخواست/پاسخ، به [API_REFERENCE.md](../reference/API_REFERENCE.md) مراجعه کنید.

## 💻 CLI داخلی

OmniRoute یک CLI داخلی (`omniroute …`) برای راهاندازی، عیبیابی و کنترل زمان اجرا ارائه میکند. این ابزار **از صفحه «ابزارهای CLI» در داشبورد جدا است**؛ آن صفحه CLIهای شخص ثالث (Claude Code، Cursor، Codex، Cline و …) را پیکربندی میکند تا بتوانند با OmniRoute ارتباط برقرار کنند.

```bash
omniroute setup                    # راهنمای تعاملی (رمز عبور، ارائهدهندگان، ترکیبها)
omniroute setup --non-interactive  # مناسب برای CI
omniroute doctor                   # عیبیابی سلامت (دایرکتوری داده، پایگاه داده، ارائهدهندگان، پورتها)
omniroute providers available      # فهرست ارائهدهندگان پشتیبانیشده
omniroute providers list           # فهرست اتصالهای پیکربندیشده
omniroute providers test <id>      # آزمایش زنده اتصال یک ارائهدهنده
omniroute combos list              # فهرست ترکیبها
omniroute combos switch <name>     # تنظیم ترکیب پیشفرض
omniroute models                   # فهرست مدلهای موجود (--json، --search)
omniroute keys add | list | remove # مدیریت کلیدهای API از ترمینال
omniroute backup                   # تهیه اسنپشات از پیکربندی و پایگاه داده
omniroute restore [<timestamp>]    # بازیابی از یک اسنپشات
omniroute health                   # جزئیات سلامت (قطعکنندهها، کش، حافظه)
omniroute quota                    # میزان مصرف سهمیه ارائهدهنده
omniroute mcp status               # وضعیت سرور MCP
omniroute a2a status               # وضعیت سرور A2A
omniroute tunnel list|create|stop  # تونلهای Cloudflare/Tailscale/ngrok
omniroute reset-password           # بازنشانی رمز عبور مدیر
omniroute --mcp                    # راهاندازی سرور MCP از طریق stdio
omniroute --port 3000              # راهاندازی سرور روی یک پورت سفارشی
```

نکته: `omniroute doctor --json` را با ابزار پایش خود همراه کنید تا درباره اتصالهای ناسالم ارائهدهندگان هشدار دریافت کنید.
